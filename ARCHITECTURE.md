# Architecture

How the code is organized, and how to add to it without stepping on each other. Read this before adding a feature.

## Layout

```text
addon/                         In-game Lua addon work, not part of the web build (see docs/design/loot-addon.md)
data/loot/                     Loot table captures: item ids per creature, one file per dungeon or raid (see data/loot/README.md; npm run check:loot)
tests/
  rules/                       Firestore and Cloud Storage rules tests, run on the emulators (npm run test:rules)
  unit/                        Tests of pure functions, run by Node directly (npm run test:unit)
  raid-coverage/               Tests of the shared buff and debuff coverage module, run with the unit tests (npm run test:unit)
src/
  main.tsx, index.css          entry point and design tokens
  App.tsx                      composition root: shared state, hooks, and the layout of the shell
  App.css                      shared layout and primitive styles (global)
  firebase.ts guildApi.ts      core: Firebase client, record types and write helpers
  useGuildData.ts              core: live subscriptions to the guild collections
  useGuildSession.ts           core: sign-in and membership
  security.ts                  core: UI-side role predicates (UI only; Firestore rules decide)
  AccessScreen.tsx             sign-in and access-request screen (not a tab)
  authErrors.ts                core: friendly text for Firebase Auth error codes (used by AccessScreen)
  shell/                       the frame around every tab
    tabs.ts                    the tab registry
    Sidebar, Topbar, PageHeading, StatStrip, WorkspacePanel, ModalHost
  features/                    one folder per feature
    roster/ teams/ calendar/ scheduled-raids/ loot/ access/
  shared/                      things two or more features use
    tabs/types.ts              the contracts: TabDefinition, TabContext, ModalRenderer
    ui/                        Modal, ArtIcon, EmptyRow, RolePill, ClassAvatar, ErrorBoundary
    game/                      class/spec data and the raid team definitions
    lib/dates.ts, art.ts, normalize.ts
```

Dependencies point one way: `shared` and the core files at the top of `src/` import nothing from `features` or `shell`; a feature imports `shared` and the core files, never another feature and never `shell`; `shell` imports a feature only through its `tab.tsx`; `App.tsx` imports `shell`. If two features need the same thing, move it to `shared` in its own small change.

## How a tab works

Every tab is one `TabDefinition` (`shared/tabs/types.ts`) exported from its feature's `tab.tsx` (the loot feature exports two, `prioritiesTab` and `historyTab`) and listed in `shell/tabs.ts`. The shell reads that definition to draw the sidebar entry, page title and hint, the search box, the toolbar, the content, the record count and the footer. A feature never edits `App.tsx` to appear.

The shell passes each tab one `TabContext`:

| Field | What it is |
| --- | --- |
| `data` | the live guild data (`roster`, `readiness`, `assignments`, `priorities`, `awards`, `afkEntries`, `raids`, `raidZones`, `settings`, `members`, `joinRequests`, `characterRequests`), readiness/request loading and error state, `leadershipLoaded`, and `unreadable`, how many documents were skipped because they could not be read |
| `query` | the current search text |
| `identity` | `uid`, `displayName`, `canEditRoster`, `canEditRaidData` |
| `shell` | `raidView` and `setRaidView` (the 10/20/40 selector lives in the shell so it survives tab switches) |
| `feedback` | `busy`, `setBusy`, `setMutationError`, `setNotice` (one shared banner and busy flag) |
| `openModal(render)` | opens a dialog (see below) |
| `navigate(id)` | switches tab; ids are matched as strings, an unknown id is ignored (and logged in development); does not clear the search text |

A new `TabContext` object is built on every render, so do not put `ctx` or `ctx.openModal` in a hook dependency array.

`TabContext` deliberately carries no role string. Role display and the "VIEW AS" preview live in `App.tsx` and `shell/Topbar.tsx` only. The `identity` booleans decide which controls to show; Firestore rules decide what direct client access is allowed. Availability and raid-response writes are server-only: their authenticated callables check the real account's membership and ownership. Never put an authorization decision in the UI alone, and never pass a previewed role to a data hook or a write helper.

## Adding a tab

1. Create `src/features/<name>/` with a content component, `<Name>Tab.tsx`, taking `{ ctx }: { ctx: TabContext }`.
2. Add `src/features/<name>/tab.tsx` exporting `<name>Tab = { id, label, art, hint, panelTitle, recordCount, footer, Content, ... } as const satisfies TabDefinition`. Write it exactly that way, without a `: TabDefinition` annotation, so the `id` stays a literal; the registry fails to compile if an id widens to `string`. Optional fields: `search`, `navCount`, `guildLeaderOnly`, `HeadingActions` (buttons beside the page title), `Toolbar` (controls beside the search box). Naming: the definition is `rosterTab`, the content component it points at is `RosterTab`.
3. Add one import and one line to the `tabs` array in `src/shell/tabs.ts` (one entry per line, so two people adding tabs rarely conflict). The order of that array is the sidebar order.
4. Import any new artwork from the feature itself (`import art from '../../../Art/...'`). `shared/art.ts` is the list of art the existing shell and features use; avoid editing it so two people don't both append to it.
5. Add a stylesheet for the feature if it needs one (see CSS below).

## Dialogs

Open a dialog with `ctx.openModal(({ close, live }) => <MyModal ... close={close} live={live} />)`. One dialog is open at a time; `shell/ModalHost.tsx` renders it after the main content and remounts it on every open.

- Capture the thing being edited (an award's priority, a player) in the closure when you open the dialog, and compute anything that must not change while it is open (such as a default date) in the click handler before calling `openModal`, not inside the renderer.
- Read everything that changes (`busy`, identity, data) from `live`, never from the `ctx` you opened it with, or the double-submit guards go stale.
- The renderer is a single JSX return of your modal component and contains no hooks. Put hooks inside the modal component.

## Data and rules

### Independent standing teams and scheduled working rosters (RAID-011)

Local implementation, not deployed. `teamAssignments/{characterId}` retains the original 10-player assignment (`blue/yellow/red/white`). `teamAssignments20/{characterId}` holds `green/pink`; `teamAssignments40/{characterId}` holds `brown`. Larger-team collections start empty; never derive or backfill them from tens. Each size is independent. The new UI uses authenticated `changeStandingTeamAssignment` for all sizes; it checks real leader membership, readiness, per-team capacity and player identity in a transaction, with a server-only per-team lock to serialize additions. Existing legacy 10-player direct-write rules are unchanged (the previously documented RAID-010 gap); new 20/40 collections are server-write-only. Reads remain available to active guild roles. Keep every size's assignment when characters are renamed or promoted; IDs do not change.

`createScheduledRaid` atomically creates the raid's zone snapshots/start instant and `raids/{raidId}/planning/working`. The new UI no longer creates raids directly. Existing/older-client raids have no working roster until a leader explicitly calls `initializeScheduledRoster` before start; copy current standing teams once, never pretend this reconstructs past assignments. Invalid source capacity/same-player conflicts in a used size fail explicitly without silently excluding characters. Missing larger-team assignments mean empty teams.

The version-1 working document contains:

- `schemaVersion: 1`, a monotonically increasing `revision`, `createdAt`, `updatedAt` and `initializedBy`.
- `invitations: { uid, mainId }[]`: one per active reciprocal-linked account with a ready main. Readiness, roster and membership triggers append newly eligible accounts until start, idempotently; existing invitations are retained. No private membership email/notes are copied.
- `lineups: { size, teams: { key, name, characterIds }[], bench: characterId[] }[]`: independent copies for 10/20/40 made at creation, with names captured then. Only sizes currently used by the raid are editable; if a size is later added, its original creation-time copy is used, not current standing assignments. Each character appears at most once per size; main/alt conflicts are checked within each individual team, not across distinct teams.

`changeScheduledPlacement` checks real Guild/Raid Leader membership, start/cancellation, current revision, ready/owned signup-selected character (ready main before any response), team capacity and same-player conflicts. Removing a copied/stale/unready position remains possible. Absent/unavailable placement requires explicit acknowledgment and does not edit the member's response. Pre-start changes have no visible audit-history requirement.

`saveRaidResponse`, availability callables and absence synchronization clear all that player's scheduled team/bench positions on Absent/new unavailability in the same transaction as the response. The working document serializes those writes with leader edits. Triggers do not repeatedly clear existing Absent positions: an explicit later leader override persists; a new response/event can clear it again. Removing unavailable dates never restores positions or changes retained Absent to Accept.

`shared/raids/ScheduledRaidRoster.tsx` is reused by Dashboard/Calendar through `RaidSignupModal`; all active guild members can view every team and bench without a response prerequisite. Subscriptions use the actual signed-in session, never VIEW AS. Leadership missing responses use the persistent invitation list, while standing coverage selects the independent assignment map for the requested size. Raid Teams available lists filter by readiness before Hide alts; assigned unready characters and their coverage remain visible.

The at-a-glance scheduled roster displays all invitees grouped by scheduled team, then assigned bench, then unassigned, alphabetically within each group. Unready/Absent invitees and copied non-invited positions remain visible. An invitee already represented by a placed main/alt is not duplicated in unassigned when their response selects a different character. There is no separate invited-raiders/absences list. Cards reuse the spec avatar and class colors, with a non-interactive response indicator. Display inclusion never relaxes backend readiness/ownership requirements for new placements.

`features/scheduled-raids/` provides the Scheduled Raids tab to every active guild role, as a list of collapsed raid rows: a row's banner (`shared/raids/RaidBanner`), name, date, time, zones and status chip come from the raid record alone, so a closed row starts no listener, and opening it mounts the panel (actions and roster) whose response and planning subscriptions run only while it is open (a closed `<details>` still mounts its children, so `RaidRow` renders the panel only when open). A raid is listed from the moment it is scheduled until 5 hours after its start, cancelled or not, and then leaves the list; Raid History keeps it (`groupRaids.ts`: a raid with no saved start time has no moment to count from and is not listed, and `isClosedRaid` is the server's `open` test, which makes a started or cancelled row read-only). The tab's clock wakes at the next start or departure rather than every second. The sign-up dialog's "Open Scheduled Raids" opens the named raid's row and scrolls to it, or, for a raid that has left the list, points to Raid History. `shared/teams/` owns the available pool, team cards and role composition used by both standing and scheduled workbenches. Scheduled coverage uses only the selected saved lineup, with captured team names; the available pool uses only that raid's invitees and excludes characters already placed for that size. Unlike the popup's account grouping, the management pool exposes a selected alt even when a copied main is still placed, so leaders can resolve the mismatch manually. Hide alts affects only the available pool. Missing assigned characters remain counted, visible and removable. Drag/drop and keyboard controls call `changeScheduledPlacement` with the current revision; absent/unavailable placement opens explicit confirmation. Both the workbench and the clean at-a-glance view subscribe to the same working plan, so changes propagate live without touching standing assignments or member responses. Members get read-only cards and response summaries. Only Guild/Raid Leaders see planning-review warnings and placement/initialization controls; VIEW AS may hide these but never authorizes writes. Closed raids remain read-only even for leaders. This is presentation-level separation of derived review warnings, not a new backend confidentiality boundary: existing member access to readiness, invitations and roster documents is unchanged. My dashboard's Upcoming raids reuse the banner (RAID-017): `DashboardTab.tsx` adds a `.dash-raid-art` element holding `RaidBanner` as the **last** child of each row, and `DashboardRaidArt.css` puts it first across the row with `order: -1`, because `Dashboard.css` styles the row's text as `li > span:first-child` and no existing child may move. The strip has a fixed 40px height, so nothing shifts while pictures load, the text and the sign-up button stay on the plain surface below it, and nothing is read for it (`zoneArt` and `zoneColors` are already in `ctx.data`).

Each scheduled team shows response totals for its displayed characters instead of open-position text: Accepted / Tentative / Absent / Not Responded, with Late and voluntary Bench included when present. Counts use the same account response as each card, including alt-mismatch cases, not the response of a similarly named character or another team's members. The team header still shows occupied positions and capacity.

**RAID-001 automatic start snapshot:** `functions/raidStartSnapshot.js` runs daily at 9:00 PM in `America/New_York`. It captures `planning/working`, signups, invitations and character/account display fields copied at capture time when the first successful execution occurs at or after the authoritative scheduled start. It uses `startsAt` and audit timestamps to discover changes in a bounded checkpoint window, then reconstructs a surfaced raid from its complete revision history so cancellations and reschedules across windows cannot erase a due start. A cancellation before start or a reschedule before the old start does not produce a snapshot. It never falls back to standing assignments.

The fixed manifest is `guilds/{guildId}/raids/{raidId}/snapshots/start`. The manifest stores the historical raid details, scheduled start, actual capture timestamp, counts, schema version and publication state. Separate `lineups/{size}`, `characters/{characterId}` and `accounts/{uid}` documents preserve each applicable group/team name and placement, assigned benches, stable IDs, copied display details, invitations and signup responses. Server writes are create-only for children; the manifest remains `capturing` until every child has been written and verified, then becomes `complete`. Firestore rules expose only complete snapshots to active guild members and deny all client writes. Partial captures are hidden; deterministic retries resume identical data without overwriting it. Missing or invalid working rosters create a terminal server-side failure record and log entry, never an inferred roster.

The scheduler is at-least-once, not real-time. A global checkpoint limits each execution to at most seven days of `startsAt`/audit timestamp ranges; the first run bootstraps one millisecond before the preceding Eastern 9:00 PM boundary so a raid exactly at that boundary is not skipped. If more than seven days were missed, later daily runs advance through bounded windows. Candidate raid jobs are durably queued before advancing the checkpoint; pending jobs retry on later daily executions, and one raid's failure does not stop other jobs. Incomplete audit histories and invalid working rosters are recorded as terminal failures; they do not retry indefinitely. `capturedAt` records actual publication time. If a retry finds changed source data during an incomplete capture, it records a terminal failure rather than publishing a mixed snapshot. Cloud Scheduler is not emulated by `npm run dev:emulator`; automated tests invoke the sweep worker against the local Firestore emulator and do not verify deployed scheduler delivery. This snapshot is not attendance or proof of participation. Audited in-raid corrections and bench-ready evidence remain separate RAID-003 and RAID-005/006 work. Never reuse award snapshots or touch loot history for raid planning.

**RAID-002 Raid History:** `features/raid-history/` registers the read-only Raid History tab and its Audit Info subtab. The current guild raid records are used only to enumerate raid IDs; the feature queries each raid's `snapshots` subcollection for `status == complete`. Each published manifest and its applicable lineup records produce individual team reports without creating duplicate snapshots. It loads character records only for the selected report and account/invitation/signup records only when expanded. Historical display values come exclusively from the immutable snapshot, never current rosters, assignments, membership or signup data. The equality query uses Firestore's automatic single-field index; no additional catalogue or composite index is needed. Snapshot rules remain the authorization boundary, including query access for active members and denial of client writes.

### Leadership and character readiness

`features/leadership/` defines the Guild Leader-only Leadership Overview tab, between Loot priorities and Member access. It is the sole location for the leader character-request review queue; members retain their own requests on My dashboard. It reuses the shared character-request queue and the coverage module in `shared/raid-coverage/` (also used by Raid Teams). No feature imports another feature. Selected-raid sign-ups use a scoped live subscription; roster, memberships, raids, assignments and readiness must finish loading before response counts are shown. Failures and unreadable records are not treated as empty results.

`guilds/{guildId}/characterReadiness/{characterId}` stores `{ ready, updatedBy, updatedAt }`, independently of roster details and account links. Missing means not ready. All active guild roles read; Guild Leaders can set any existing character, while members (including Raid Leaders acting for themselves) can set only their reciprocal linked main and unlinked direct alts. Firestore rules enforce exact fields, boolean readiness, authenticated writer and server time; deletes are denied. Character IDs keep flags stable through renames and main promotion, without widening roster-edit permissions. `useGuildData` subscribes using the real session, never VIEW AS, and ignores pending readiness writes until their server timestamps resolve.

My dashboard has per-character readiness controls; Guild Leaders also manage them in the roster's App access column. RAID-011 Leadership counts responses against that scheduled raid's retained invitation list (main-ready eligibility), replacing the historical any-ready-owned-character population. Any response counts; Accept/Tentative/Late on an unready or no-longer-owned character gets a separate warning, even when the account has no ready characters left. Not-invited/unlinked setup counts remain explicit. Readiness never modifies sign-ups or represents attendance. Coverage uses independent current standing assignments and retains provisional-data warnings.

`useGuildData` subscribes to the guild's collections once and every tab reads them from `ctx.data`. Writes go through `guildApi.ts`. `navCount`, `recordCount` and `footer` are functions of `ctx.data`, so today a tab can only show counts for data the shell already loads. If a feature needs its own collection, agree on how it loads that data (a hook inside its content component, or a new shared subscription) before building it. Adding a new collection currently touches shared files: the record type and write helper in `guildApi.ts`, a subscription in `useGuildData.ts`, and a block in `firestore.rules` (Firebase deploys a single rules file) with its tests in `tests/rules/` (see "Testing the Firestore rules" in `CONTRIBUTING.md`). Do each in its own small commit and say so in the PR so a reviewer looks at the rules change on its own. Rules are the authorization boundary, so a feature that writes data needs a rules change and a rules deploy before the hosting build ships.

Roster comment review uses `useRosterComments` through `useGuildData`: Public comments are subscribed for authenticated members; Leadership collection subscriptions use only the actual Guild/Raid Leader role, never VIEW AS. A session-only Show Comments toggle beside All characters/Hide alts replaces the normal columns with Character, Public and (for leaders) Leadership comments. Comments use small-text previews and tap/click/keyboard-triggered native popovers, which float above the table without changing row height. Comments appear on the character with the linked account; unlinked alts do not inherit another account's comments. Loading, empty and failed reads are distinct, and unreadable records are reported. The Leadership column is hidden in a Member preview without changing the real-role subscription. Authors continue editing both audiences on the dashboard; existing Firestore rules allow authors to read their own Leadership comment but deny other members' private comments and collection lists.

Award snapshots are immutable: the candidate order and council note are copied from the priority as it was when the award dialog opened (`features/loot/AwardModal.tsx`) and the rules compare them to the stored priority. Do not change that flow casually. A manual award (no `priorityId`, for a decision made without a priority list, such as a roll) has no snapshot at all: it is recorded with a roster character's id and a `decision`, and the rules accept it only together with its audit entry (see [audit-first-loot.md](docs/design/audit-first-loot.md#manual-awards-loot-002)). Leaders record one from **Record loot** (`features/loot/ManualAwardModal.tsx`; `manualAward.ts` builds the award from the form and `guildApi.recordManualAward` writes it with its entry, listing `manualAwardCreateFields`, which has the `decision` that `awardCreateFields` lacks); a rules test runs the form's own payload through the real rules. The form asks for the dungeon and the boss apart and `encounterOf` joins them as "dungeon · boss" (a dungeon alone as "dungeon ·"), the form `splitEncounter` and the Log's dungeon filter read. Guild and Raid Leaders fix a mistaken receipt on the item itself: unlocking the item shows an x next to RECEIVED (`features/loot/PriorityList.tsx`), which opens `features/loot/ReceiptFixModal.tsx` to move the receipt to someone else or remove it (`guildApi.correctAward`, `removeAward`; `listingProgress(...).receipts` says which award a received line stands on). An award is never deleted, a removed one is marked `status: 'removed'` and stops counting (`isRemovedAward` in `shared/game/completion.ts`; completion, My dashboard and the header total all skip it), and the Log, which has no edit or delete control, keeps every earlier version. On a desktop window (1101px and wider) the card is laid out as item, place and note, council order by `PriorityList.css` alone: the wrappers `.priority-main`, `.priority-item-line` and its inner div are `display: contents` and their children are placed on the card's grid by class, so the order of those children in `PriorityList.tsx` matters (the comment in the CSS says so).

Raid sign-ups live at `guilds/<guildId>/raids/<raidId>/signups/<uid>`. `raidSignups.ts` owns the per-raid subscription and calls the server to save responses; `shared/raids/RaidSignupModal.tsx` is shared by Calendar/Dashboard, without adding a global subscription. Each response stores a character ID, status, server timestamp, and `benchKind: 'self'` only for Bench. Buttons save immediately with response-specific colors. The separate full scheduled-roster view is available to every active guild member before or after any response, including Absent/Bench; it no longer infers a team from the saved character's live standing assignments. No immutable starting roster is saved yet.

Each upcoming dashboard raid subscribes while mounted so its compact, centered action shows the current account's response above "Click to change or view details", or "Sign-up / roster" before a response. Unavailable dates display Absent immediately while server synchronization catches up. The action sits beneath the raid details and unavailable/cancelled badge visually, without reordering the existing row markup.

`functions/index.js` exposes authenticated callables implemented in `functions/raids.js`. Firestore rules deny all direct writes to `afkEntries`, sign-ups and server-only `availabilityLocks`; other collections retain their existing authorization rules. The server rechecks guild membership, reciprocal main/direct-alt ownership, cancellation and the start cutoff, and queries actual unavailable ranges. It never trusts caller-supplied uid, display name, team, timestamps or bench provenance. Availability changes and response saves share a transaction lock at `guilds/<guildId>/availabilityLocks/<uid>`, preventing stale concurrent writes. Adding an event atomically saves Absent on overlapping upcoming raids; deleting an event leaves Absent, even for legacy events not yet backfilled. Unlinked accounts can record unavailable dates without fabricating a character response.

Firestore triggers synchronize newly scheduled/rescheduled/restored raids and newly linked mains. They re-read current state in transactions, so delayed/retried events cannot resurrect an old response. `shared/raids/availability.ts` derives effective Absent for every roster preview while triggers catch up. All overlapping events must be removed before manual responses are allowed; removing them does not restore the previous response. Started/cancelled raids are not rewritten by automatic synchronization. A Guild Leader-only Settings action runs the idempotent initial backfill. See README for Functions setup and deploy order; these server handlers are tested against the local Firestore emulator in `functions/raids.test.js`.

MEMBER-005 adds `updateUnavailableDates`, using the same authenticated account lock and ownership checks as add/remove. It updates the original `afkEntries` document's dates and server `updatedAt`, preserving owner, display name and creation metadata. It reads raids in the union of the old/new ranges (not the gap between disjoint ranges), retains/materializes Absent for old coverage and applies Absent to new coverage atomically with placement clearing. Previously cleared placements are never restored; all unavailable entries must be edited or removed so none overlap before a manual response can be saved. Started/cancelled raids and immutable snapshots are untouched. A single prefilled `shared/availability/AbsenceModal.tsx` is used by dashboard and calendar; feature code never imports another feature. Deploy the callable before Hosting; no migration.

The Guild Calendar's **Show:** toggles (UX-007, `features/calendar`) filter data the page already holds. `calendarLayers.ts` is the pure rule (`raidsOnDay`, `absencesOnDay`, `withRaidsShown`, `hiddenNote`, so Node can test it) and `useCalendarLayers.ts` keeps the choice for the page session in a module-level store read with `useSyncExternalStore`, like `features/roster/altVisibility.ts`, because the toolbar (`CalendarToolbar.tsx`) and the grid (`AfkCalendar.tsx`) are separate components. Nothing is saved and no Firestore read or listener depends on it. `AfkCalendar` filters only what the day cells draw and name: "Your date ranges" and the edit dialog read the unfiltered `entries`, and the panel heading, footer and sidebar count in `tab.tsx` stay guild totals. With both off a status line sits between the month header and the grid; nothing is added inside `.afk-calendar-grid`, whose `:nth-child(7n)` rule depends on its children. A link to a raid (`ctx.navParam`, from Scheduled Raids or Leadership) turns Raids on in an effect keyed on that id, and the scroll to that raid happens once per arrival (`scrolledTo` in `AfkCalendar.tsx`), so pressing a toggle never pulls the page back to it. `CalendarLayers.css` lets the shell's `.toolbar-controls` wrap on a phone with `:has(.calendar-layers)`, as Roster and Loot already do, instead of adding a wrapper element.

New raids store `startsAt` from the server's validated Eastern date/time conversion in `functions/raidPlanning.js`; audited edits use the equivalent client helper in `shared/lib/raidStart.ts`. Saving an older raid initializes its start instant; rescheduling updates it in the same audited change. Nonexistent spring-forward times are rejected and the repeated fall hour uses its first occurrence. Older raids without `startsAt` remain readable/editable, but manual sign-ups and planning are closed until a leader saves their details; initializing their working roster is a separate explicit action. Start cutoff closes working-roster edits, not an automatic immutable snapshot.

Deploy the new Functions/callables and matching Firestore rules before publishing the RAID-011 client (only when deployment is requested). Old clients may still create raids without a working roster; use explicit initialization, never a silent live-team fallback. Existing 10-player assignments/names remain intact; larger standing collections are intentionally empty until leaders populate them. No data migration is required, and no award/audit documents change.

### Item tooltips

Item names, icons and tooltips are read live from Wowhead's public tooltip endpoint by item id (`shared/game/itemTooltip.ts` has the addresses; `shared/lib/itemInfo.ts` keeps an in-memory cache, runs four requests at a time and retries once; `shared/ui/ItemTooltip.tsx` shows an item as a chip that opens its tooltip when a mouse rests on it and on click, tap or Enter; hover is a mouse-only convenience, since touch and keyboard have no hover). The tooltip HTML comes from a third party, so it is never put into the page: `sanitizeTooltipHtml` reads it into a tree of allowed elements and allowed class names (no links, images, styles or scripts), and the component renders that tree as ordinary React elements with prefixed class names. Use `ItemTooltip` wherever an item id should show a tooltip; a failed lookup leaves the id (or a typed name) in place, so manual entry never depends on Wowhead. Capture files in `data/loot/` hold ids only (see `data/loot/README.md`).

### Priorities from the drop lists

A leader can tick items in Browse drops (`features/loot/DropsBrowser.tsx`) and add them to Loot priorities. Each becomes a priority with a fresh id (one per item per phase is kept by the dialog, which marks an item already on the list; see the audit section for why ids are not reused), the item's Wowhead name as `item`, `encounter` in the same "dungeon · boss" form as one typed by hand, an empty `rankedPlayers` ("Needs players"), and the optional `itemId`, `zoneId` and `npcId` that say where it drops (`PriorityRecord` in `guildApi.ts`; the normalizer drops any that is not a positive whole number). A priority with an `itemId` shows its real name, icon and tooltip through `ItemTooltip`; one typed by hand looks as before. An item counts as already listed when a priority has its id or, for a hand-typed one, the same name (`prioritiesForItem` in `dropsFilter.ts`). In the dialog a ticked box means "on the list of the phase picked in its Phase dropdown": ticking an unlisted item stages an add, unticking a listed one stages a take-off, and nothing is written until the bar at the bottom is used. Add all and Remove all stage a whole dungeon, whatever the search and the filters show. Beside the search the dialog has two filters: one creature of the zone and an item slot (`filterGroups` and `DropFilters` in `dropsFilter.ts`, pure so Node can test them; the slot of an item is read through `useSlotOf` once it has been looked up, and every item of the zone is looked up when it is opened). They only decide what is shown. The dropdown offers only the current phase and the next one (`phaseOptions` without the finished ones), because a finished phase is a read-only record. Taking off an item with no players deletes its priority (`deletePriorities`). Taking off one that has players asks once more and **keeps** it: the priority is written with `hidden: true` (`setPrioritiesHidden` in `guildApi.ts`, logged like any edit) and keeps its candidates, note and the awards recorded from it. `useGuildData` splits the documents, so `priorities` and `allPriorities` hold only visible ones and `hiddenPriorities` the kept ones; nothing else in the app sees a hidden priority, and an award cannot be recorded from one. Ticking the item again clears `hidden` instead of creating a new priority, so the candidates come back as they were and the awards still point at it. Awards keep their own copy of the candidate order either way, so taking an item off never touches history. The member dashboard reads the candidate lines like the rest (see Candidates by roster id).

### Drop lists the guild can edit

The built-in drop lists (`data/loot/*.json`, one capture per zone) are the starting point; Guild and Raid Leaders change them in the app without a release (`features/loot/TablesEditor.tsx`, opened from Browse drops with "Edit the drop lists"). The changes sit on top of the captures and never rewrite them, and **they belong to a loot phase**: one phase can have one set of zones and loot and another phase another. **A phase starts from nothing**: no zone is in its lists until a leader ticks it, and it has none of an earlier phase's creatures or items. It can instead **follow** an earlier phase, which gives it that phase's lists with its own changes on top; when the followed phase is finished nothing in it can change, so the follower simply carries on from where it ended. The editor has a collapsible Zones section: the phase is picked inside it, so one phase's checklist is on screen at a time however many phases there are, with a Follows choice (Nothing, or an earlier phase) and the zones in collapsible groups (`groupZones` in `features/loot/zoneGroups.ts`: dungeons, then raids by size; a group with no zone is not shown). Below it are the creatures and items of one zone of the phase picked.

They live in the guild's `lootTables` collection. A document carries the phase it was written in (`phaseNo`, the number priorities and awards carry). The lists of phase N are the captures with the documents of N's **follow chain** applied in phase order: N itself, the phase N follows, the phase that one follows, and so on (`followChain` and `mergeTables` in `shared/game/guildTables.ts`, which has no runtime imports). A zone is in the lists when the latest zone document of the chain that says so puts it in (`removed: false`); with none, it is out. Creatures and items fold over the same chain. The name, kind and size of a zone the guild made come from its zone documents of any phase up to N, so it is the same zone wherever it is ticked. A change made in phase N never reaches an earlier phase, and reaches a later phase only if that phase follows N. Only the current and the next phase can be written (the rules, like priorities), so a finished phase's lists are a record. There are four kinds of document, with ids that carry the phase: a **custom zone** (`z{zone}_{phase}`, a zone number from 50 million up so it cannot clash with the game's own, with its name, kind and size, and `removed: false` in the phase it is made), a **zone presence** document for a zone of the captures (`z{zone}_{phase}`, with only `removed`: whether the zone is in the lists in that phase), a **phase** document (`p{phase}`, only `follows`: the number of an earlier phase, or none), and a **creature** (`s{zone}_{key}_{phase}`, also the zone-wide list with the key `zonewide`). A creature document is a delta: `itemIds` added in that phase and `hiddenItemIds` taken off from that phase on (they were there before: the capture's or an earlier phase's), plus its name, kind and place and an optional `removed` (true or false). A creature the guild added has a random key; a creature of a capture has `npc{number}`.

`dropTablesOf` gives Browse drops the zones in the lists in a phase, so the item list, the tick boxes, the boss order of Loot priorities (`useBossOrder`, by the phase being looked at) and Carry over all follow the phase. `readTableDoc` reads a stored document tolerantly, `parseItemIds` reads pasted numbers and Wowhead links, and `addItems`, `takeOffItem`, `addCreature`, `moveCreature`, `addZone`, `setZoneInPhase`, `setZonesInPhase`, `setFollows` and the rest build the writes for the phase being edited. An item can be on one creature per zone in a phase (as in a capture): the editor reports where an item already is instead of adding it a second time.

Each change is one audited write, like a priority (`writeLootTables` in `guildApi.ts`, entry `table_{id}_{rev}`, the rules in `validTableCreate` and `validTableEdit`, and the `table` branch of the entry rules). A table is never deleted: an entry id can be used once, so a deleted id could never be created again, and the id of a table is made from its zone, key and phase. Taking something away is an edit that sets `removed: true`, and `removed: false` brings it back, which keeps the items. The rules cap the sizes (at most 80 items added and 80 taken off per document, 100 characters of name) but cannot check each entry of a list, so the client reads the lists tolerantly (`readTableDoc` keeps only whole item numbers). The Log shows these entries under "Drop lists" with the phase they are about ("Added 6 items to Ghamoo-ra in Blackfathom Deeps (Phase 2)", "Phase 2 now follows Phase 1"); it names zones and creatures from every phase (`mergeTables(..., true)`). `useGuildData` subscribes to the collection for every role; an error reading it only warns, so the built-in lists keep working before the rules are deployed.

### Zones and their colors

Every zone the guild has is in one list (`listZones` in `shared/game/zoneList.ts`, read into `data.zoneList` by `useGuildData`): the zones of the built-in drop lists (`data/loot/*.json`, loaded by `shared/lib/dropTables.ts`; they just show up), the zones a Guild Leader adds on the Zones page of Settings, and the zones of the older raid zone list (the `raidZones` collection, still read, renamed, resized and removed there). A zone added in Settings is kept **with the drop lists**: `addZone` writes its first zone document (name, kind, size; no `removed`, so it is in no phase until ticked) in the current phase, audited like any drop list change, so it is there for loot (ticked into a phase in the drop list editor, which no longer adds zones) and for raid scheduling alike: `schedulableZones` turns the raids of 10, 20 and 40 into the calendar's picker (`data.raidZones`; the id of one made in Settings is `z` and its number, so a raid's saved zone details keep working). The Zones page (`features/settings/ZonesPanel.tsx`) groups the list like the editor (`shared/game/zoneGroups.ts`).

A zone has a **key**: its number, or `r-` and the id of a zone of the older list. Its color (`shared/game/zoneColors.ts`, no imports) is the one a Guild Leader chose for the key, else an automatic one made from the key alone (nothing names a zone). The choices are one document of their own, `settings/zoneColors`, so a save of the general settings from an older app cannot wipe them: a `colors` map from zone key to `#rrggbb`, written only by a Guild Leader by merging (so one pick touches one zone), read into `data.zoneColors`. The rules count the entries (at most 200) but cannot look at each one, so `readZoneColors` keeps only a zone key with a valid color. A zone made in Settings has its color chosen as it is made (`suggestColor` offers one no zone has yet); `spreadColors` gives the zones that have none their own colors. The sixteen colors of the palette (offered by the `ColorSelect` dropdown in color order, with Other for any color) are mid-tones of about the same lightness, so a bar or a dot in one is at least 3 to 1 against both the light and the dark panels (`tests/unit/zone-colors.test.ts` computes it); text is never set in a zone color, chips and tints are made from it with `color-mix`. `features/loot/useZoneColors.ts` turns a priority into its zone's color: by `zoneId` when it came from Browse drops, else by the dungeon its encounter names ("Dungeon · Boss") looked up among the zones of every phase. The stylesheets of Loot priorities, Browse drops and the drop list editor read it from the inline custom property `--zone-color`; the dot is `shared/ui/zoneColor.css`.

A zone's **artwork** is a picture a Guild Leader uploaded for it, so a new zone needs a picture and a pick, never a release. The pictures are files in Cloud Storage, governed by `storage.rules`: `guilds/{guildId}/zone-art/{imageId}/full-{rev}.jpg|png|webp` and a small `thumb-{rev}.jpg`; any member of the guild reads, only a Guild Leader adds or deletes, a file is never overwritten (replacing a picture uploads the next rev), and a picture is at most 5 MiB, a small copy 300 KiB. Which pictures exist and which one each zone uses is one more settings document, `settings/zoneArt` (`images`: a map from a picture's id to its name, address, size and rev; `art`: a map from a zone key to a picture's id; at most 200 of each), written only by a Guild Leader by merging, like the colors. The rules count the entries but cannot look at each one, so the app reads both maps safely and ignores what does not fit. `storage.rules` reads a person's role from the same members document the Firestore rules use, so the two services cannot disagree. The app side: `shared/game/zoneArt.ts` (imports only zone keys) reads the document and keeps a picture only when its name, size, storage paths and addresses are what the app writes (the app deletes files by those paths and puts the address in a style, so neither is taken on trust); `guildApi.ts` has `addZoneImage`, `replaceZoneImage`, `renameZoneImage`, `removeZoneImage`, `pickZoneArt` and `pickZoneArts`, each a transaction that reads the document first, uploading files with a year's cache header (a replaced picture is a new file, so no browser shows a stale one) and removing the files nothing points at; `useGuildData` reads it in the same settings listener as the colors, as `data.zoneArt`. Settings has a Zone images panel (the library: add several at once, rename, replace, remove; the small copy is made in the browser, `features/settings/zoneImageFile.ts`) and each row of the Zones page an Artwork dropdown, plus Pick pictures by name. The picture of a zone shows as a banner on its title block only (`shared/ui/zoneArt.css`, a `::before` behind the existing block, so no element is added and no child moves): the zone heading of the priority list is taller, with the picture filling the right side and fading out toward the name, and in Browse drops and Edit the drop lists a zone with a picture shows the picture and its name as a banner and nothing else (Browse drops keeps the zone's description one click away under "About this zone"); the rows of loot under a zone have none. The bucket is `VITE_FIREBASE_STORAGE_BUCKET`, or `<project>.firebasestorage.app` when it is not set. A picture is shown by its download address (a link with an unguessable token, kept in the members-only `settings/zoneArt` document), which Storage does not check against the rules: the rules decide who may add, delete, list and ask for an address, and a copied link keeps working until its file is deleted. Cloud Storage has to be turned on once in the Firebase console (it needs the Blaze plan) and its service agent given access to Firestore once (CONTRIBUTING.md, "Cloud Storage"); `npm run release` then deploys the Storage rules after the Firestore rules. The Scheduled Raids banners and the zone picker of Add Raid and Edit Raid find a raid zone's picture from the id stored on the raid (`shared/raids/raidZoneArt.ts`: `z<zone number>` is that zone number, any other id is `r-<id>`), so a renamed zone keeps its picture; they use the small copy, loaded lazily, and a zone with no picture shows a tint of its color.

### Phases of the loot lists

A phase is a number (`shared/game/phases.ts`), not a name, so renaming one in Settings cannot split its lists. Settings gets one optional field, `phaseHistory`: the names of the finished phases, oldest first. The current phase's number is its length (a guild that never closed a phase is in phase 0), and `currentPhase`/`nextPhase` stay the names of the current and next phase. A priority and an award carry `phaseNo`; none means phase 0, so everything recorded before phases existed is the first phase and nothing is migrated. A priority can also carry `carriedFrom`, the id of the priority it was carried over from.

`useGuildData` keeps `priorities` as the **current phase's** list, so the dashboard, the counters and anything written before phases need no change, and adds `allPriorities` for the Loot priorities tab, which looks at one phase at a time (`features/loot/usePhaseView.ts`; the choice is `phase` in `priorityFilters.ts`, null meaning "the current phase"). Starting a phase (the Loot phases section in Settings, Guild Leaders only, with a typed confirmation, `features/settings/PhasesPanel.tsx`) is one save of the settings document that appends the closing name to `phaseHistory`, and reopening takes it off again; no priority or award is rewritten, because the lists prepared for the next phase are already filed under the number that becomes current. The rules accept only those two moves (`validPhaseHistory`). A closed phase is read-only in the app; nothing in the rules stops a write to it yet. The target, with LOOT-001, is a priority rule that allows a write only when its `phaseNo` is the current phase's, read from Settings in the same rule. Until then an old browser tab that predates this feature writes priorities without `phaseNo` (phase 0). The same item can be on each phase's list. An award with no priority counts toward a priority of the same item name only in the same phase. My dashboard lists one phase's priorities and awards (`inPhase` in `features/dashboard/myCharacters.ts`), not every phase up to it: the current phase until a member picks a finished one (MEMBER-008). `features/dashboard/dashboardPhase.ts` is the pure rule: `dashboardPhases` offers the current phase and the finished ones, never the next, and `shownPhase` gives the current phase when the choice is not offered or was made while another phase was current, so a choice ends when the guild starts a phase. My loot priorities and My awarded loot each have their own choice, kept as state in `DashboardTab.tsx`, so a reload ends them too, and nothing is saved or read for them. `DashboardPhaseSelect.tsx` is the control, a labeled select like the Loot priorities Phase selector (each card's has its own accessible name), shown only once a phase has finished (with one phase there is nothing to pick). A finished phase lists all of the member's awards in it, where the current phase's list stops at five. Earlier phases are also in the Log and in the Loot priorities Phase selector.

### Carrying an item over

The Carry over dialog (`features/loot/CarryOverModal.tsx`) creates a new priority in the phase being looked at from one in an earlier phase: `carryOverFields` (`carryOver.ts`) copies the item, boss, note and the whole candidate list and sets `phaseNo` and `carriedFrom`; it is written with `createPriorities`, so it is in the Log. Nothing about "received" is copied. `awardsForPriority` (`completion.ts`) follows `carriedFrom` back through the priorities it names (at most 20 steps, never twice the same one) and counts the awards recorded from any of them, and unlinked awards of the same item name in any of their phases, so a carried priority shows who already got it and who still needs it, while the earlier phase's record never changes. The lookup is built from `ctx.data.allPriorities` (`usePhaseView`). The dialog has the filters of the priority list: a search, a dungeon or one boss of it and an item slot (the dialog builds the choices with `encounterOptions` and `slotChoices` and looks every item up with `requestItem` so the slot filter can tell which match; `visibleForCarryOver` in `carryOver.ts`, pure so Node can test it, applies them with `matchesEncounterScope`; `targetIndex` answers "already on the target list" from sets). They only decide what is shown: an item that is ticked stays ticked when a filter hides it, and the tray says how many ticked items are hidden.

### Candidates by roster id

A priority's candidates are lines (`src/shared/game/candidates.ts`): a character, an open note ("any warlock who didn't get X", not a person) or a finished note. The document stores them as the names it always had (`rankedPlayers`, what each line said when it was written) and a parallel `rankedIds` (a roster id, `''` for an open note, `'!'` for a finished one); a priority without `rankedIds` is read as names only and works as before. An award from a priority carries `recipientId` and `prioritySnapshotIds` the same way. Everything that compares players goes through `makeWho(roster)`, which gives a line or an award one key per person (the id, or for an old name the roster character who has that name), so completion, the filters, the Log's player filter, Carry over, the award dialog and the member dashboard follow a rename, while award snapshots and Log entries keep the names as they were written. The roster picker (`src/shared/ui/CharacterPicker.tsx`, search, by class or by name, class colors) is shared and works at once: ticking a character adds a line at the end (`addCharacters`), unticking takes the last listing of that character off (`removeLastCharacter`; `CandidateEditor` remembers where it was, so ticking them straight back puts them there, `addCharacterAt`), and a small plus lists a character again (a player may be listed twice for an item); there is no separate Add button. `CandidateEditor` in the loot feature builds the lines. An old priority is converted when a leader edits it: a name that is one roster character's becomes that character, anything else stays as a note. A receipt through an open note records the award and, in the same batch, puts the winner on a character line where the note was (`recordAwardThroughNote`). The rules side is in `docs/design/audit-first-loot.md`. A carried-over priority says where it came from; in Carry over, an item that was already carried over shows as Carried over with a **Remove** button: it asks, then deletes that copy with its Log entry (`deletePriorities`); the earlier phase's priority is never touched, so the item can be carried over again, and awards recorded from the copy stay in the awards and the Log with their own snapshot. The order of a priority's candidates is locked by default (`orderLock.ts`): the lock next to COUNCIL ORDER unlocks one item for the page session, which is what shows the arrows; nothing about it is stored.

### The audit of loot changes

Every change to a loot priority or an award is one batch of the change and its audit entry (`auditLog/{type}_{id}_{rev}`; `award_{id}_1` for a new award). The helpers are in `guildApi.ts` (`createPriorities`, `editPriority`, `deletePriorities`, `recordAward`) and nothing else writes these collections: `saveGuildRecord` is for the roster only, and the rules refuse a priority or award write without a truthful entry (`validPriorityCreate`, `validPriorityEdit`, `validPriorityDelete`, `validPriorityAward`, `validManualAward`; the entry rules are `validAuditEntry` and `auditDescribesChange`). What an entry lists is built by the pure functions in `shared/game/lootAudit.ts` (`describeCreate`, `describeEdit`, `describeDelete`), which have to agree with those rules: the fields that differ, each with its old and new value. A priority also carries `rev`, `updatedBy` and `updatedAt`, stamped by the rules, and can be written only in the current phase or the next one. A long list is written in batches of `AUDITED_BATCH_SIZE` (10) because a batch has a limit on the document lookups the rules may make (the numbers are pinned in `tests/rules/batch-budget.test.ts`); each batch is all or nothing and the helpers report which ids a batch wrote. An entry id can be used only once, so every new priority gets a fresh id (`newPriorityId`): the id of a deleted priority cannot be created again. A priority taken off the list but kept carries `hidden: true`; the rules accept the field only as `true` and only on an edit (never on a new priority), and `hidden` is one of the fields an entry lists, so taking an item off and putting it back are in the Log. This is why the client needs the audited rules: an older rules file refuses the field.

The Log dialog (`features/loot/AuditLogModal.tsx`; it replaced the Award history tab, so there is no separate list of awards) listens to the newest 100 entries only while it is open (`subscribeAuditLog`), with "Load older entries", and `features/loot/auditText.ts` turns an entry into words. It filters out raid entries, adds the awards recorded before the Log began (they have no entry and no revision; `legacyAwardEntry` shows each as an entry dated the raid night) and has a find box and player, slot and dungeon-or-boss dropdowns and an order over what is loaded (`logFilters.ts` works out an entry's dungeon, boss, players and item from the entry and from the priority it is about, because an entry lists only what changed). Every line also says which loot phase it is for, and a Phase dropdown and the find box filter by it (`entryPhase.ts`: from the award or priority as it stands now, else from the entries about it, else from the id of a drop list document; a phase started or reopened is for the phase the guild is in afterwards; an entry whose phase cannot be told shows a dash and matches no phase). A Date dropdown shows one day (`entryDate.ts`: an award is on its raid night, `awardedAt` as the award stands now, else as the entry says; any other entry is on the day it was made in the viewer's own time; the raid night is a plain date, so it never shifts with time zones). Starting or reopening a loot phase is logged too (`changePhase` in `guildApi.ts`): the settings document carries `phaseRev`, how many times a phase has been started or reopened, and the entry `phase_settings_{phaseRev}` lists the phase fields (`currentPhase`, `nextPhase`, `phaseHistory`) that differ between what is stored and what is saved; the rules accept a change of the phase history only with the next revision and its entry (`validPhaseRev`, `validPhaseEntry`). The entry a write needs has to be one written in that very request (`writtenNow`), so an entry left from an earlier life of an id cannot stand in for a new one. The log can be read by every guild role and changed by nobody through the app; the owner of the Firebase project can still change anything in the console, which the rules cannot prevent. The one exception to "no deletes" is not in the app: the maintainer's one-time launch reset (`functions/launchReset.js`, run by `scripts/launch-reset.mjs` with the Admin SDK, see `docs/design/launch-reset.md`) erases the pre-launch phase's awards, loot priorities and the Log entries about them, backs them up first, then seals the guild (`settings/launchReset`) and leaves one `ledger` entry that the Log shows ("Erased the test data of ..., once, for good"). The rules refuse every client write of the seal and the entry, so nothing in the app can repeat it.

### Reading data safely

Character changes use `characterRequests` and the authenticated callables in `functions/characters.js`. Direct client writes to requests are denied, including for leaders; only the owner and Guild Leaders can read them. `useGuildData` subscribes to all requests for the actual Guild Leader role, or a `userId == actualUid` query for other active accounts, never using VIEW AS. It exposes separate loading/error state and clears records when the session/actual identity changes. `shared/characters/` owns submission, history and reusable review controls used by My dashboard and Member access; MEMBER-003 can reuse them without importing another feature. Requests retain immutable submission snapshots, server timestamps, actor identity and terminal decisions/notes. Members withdraw pending requests; Guild Leaders approve/reject. Approval rechecks active membership, reciprocal ownership, eligibility and the original character snapshot inside the transaction. A stale request stays pending with an explicit error until rejected/withdrawn and resubmitted.

Main promotion queries the current direct alts and atomically moves the reciprocal account link, promotes the selected alt and reparents the old main and all other direct alts. New alts receive a server-generated roster ID reserved in the request and are created only on approval; existing alts retain their IDs. Teams, sign-ups, loot and immutable historical snapshots are never rewritten. Legacy name-only loot matching can lose a dashboard match after a rename; the stable-ID loot migration remains LOOT-003, not this request workflow. Class/spec/default-role data lives once in `functions/characterClasses.json`, imported by the server and `shared/game/classes.ts`; the location is necessary for the Functions deployment bundle. `shared/game/players.ts` defines the roster record type, re-exported by `guildApi.ts`. Server authentication/input/membership helpers are shared with raid callables through `functions/access.js`. Deploy Functions first, rules second, then Hosting.

Member Access removal uses `shared/members/access.ts` through `guildApi.ts`: a client transaction sets the existing membership's role to `Removed`, clears `playerId` and releases the reciprocal `linkedUid`. `Removed` is a membership status, not an active `GuildRole`; existing rule predicates and server callable role allowlists deny it access. Rules enforce Guild Leader-only changes, no self-removal and restoration only to an unlinked Member. `useGuildSession` displays a dedicated removed-access screen using the account's readable own membership record, including live revocation; invalid roles fail explicitly rather than activating the app. Guild subscriptions stop and their in-memory records are cleared when access is lost. VIEW AS never participates in these decisions. Characters, assignments and historical documents are not deleted or renamed by removal, and already-downloaded data cannot be recalled.

Raid zone snapshots are compared by ordered zone values (`id`, `name`, `size`) in `shared/raids/zoneSnapshots.ts`, not by JSON text. Firestore map key order is not significant; logging an unchanged zone list as changed makes the audit entry inconsistent and the batch is refused.

The rules decide who may write and check a few shapes (a member's role, the allowed keys of a join request), but they do not require the fields the UI reads or check their types, and roster, lootPriorities and awards written by a Guild Leader are free-form. So the client does not trust what it reads. `subscribeGuildCollection` passes each document of those five collections through a normalizer in `shared/lib/normalize.ts` before it reaches `useGuildData`. A field the UI reads gets a safe default (text `''`, lists `[]`, non-string list entries dropped), every other field passes through unchanged, and a document that cannot be used (a name or item that is missing or not text, an unknown role or status) is skipped. Skipped documents are counted in `data.unreadable`, which the shell shows to Guild Leaders as "N records could not be read", and named by collection and id in a console warning. If a feature starts reading a new field from one of these collections, add it to that collection's normalizer. raids, afkEntries and teamAssignments are validated by the rules and are read as they are. `guildApi.ts` and `useGuildData.ts` import `shared/lib/normalize.ts` at runtime; `normalize.ts` must keep its import from `guildApi.ts` type-only so the two never import each other at runtime.

Guild settings (`guilds/<id>/settings/general`) are a single document read through `normalizeSettings` in the same file: it never drops the document, and every missing or invalid field falls back to `defaultGuildSettings` in `shared/game/settings.ts`. A failed read (for example rules not deployed yet) keeps the defaults and logs a console warning rather than showing an error. Anyone in the guild may read it, only a Guild Leader may write it, and the rules require exactly the expected fields (plus an optional `phaseHistory`, which can only grow or shrink by one name at a time): the two phases with a status label and tone each, the council status, and the 	eamNames (10-player) and groupNames (20- and 40-player) maps. Deploy the rules before hosting a build that saves settings.

Render errors are contained by `shared/ui/ErrorBoundary`: one around the workspace panel (reset when the tab changes), one around the dialog host (reset when the open dialog changes) and one around the whole app in `main.tsx`. A boundary adds no element when nothing has thrown, and a healthy panel stays mounted across tab switches. Once it has caught an error it stays up until its `resetKey` changes (the tab id, or the open dialog's key) or the page reloads, even if the data heals. It does not catch errors in event handlers or async code.

## Spacing

`shared/ui/spacing.css` defines the page gutter (19px, 13px on a phone: what the toolbar and the priority rows use), the gap between page cards, the card padding and corner, the side padding and indent for cards and lists inside a card, and the top padding and gap of a loot dialog. `shell/WorkspacePanel.tsx` imports it, so every tab's styles can use the variables without importing the file; use them instead of new pixel values so a new card or dialog lines up with the rest. The workspace panel has no padding of its own, so a tab's content brings its own gutter: `SettingsTab` returns the form and its panels as siblings, which is why the panels after the form take the gutter and gap with `.settings-form ~ .settings-section`. Every tab uses them except the Guild roster, a full-width table that stays edge to edge with 18px cell padding; `.scheduled-raids-tool .scheduled-workbench.raid-team-view` (the workbench inside an opened raid row) adds no padding of its own, because the tool's padding is the page's.

## Help and popovers

Use `shared/ui/HelpPopover.tsx` for explanatory help and expandable read-only text. Pass an accessible `label`, the button's `trigger` content, and the panel's `children`; `triggerClassName` can preserve an existing button layout. Do not nest it inside another button or a label, or put a mutation on its trigger. Dashboard raider-type help is a separate control so reading it cannot save a preference.

The shared component uses a native auto popover in the top layer, without a layout wrapper. Tap/click, Enter and Space toggle it; desktop coverage details also use this explicit activation instead of hover. Only one auto popover is open at once. Escape closes it and restores trigger focus. Outside pointer/click interaction, focus leaving the trigger/panel, page or nested-container scrolling, and viewport resize/scroll dismiss it. Scrolling or interacting inside the panel does not dismiss it. Navigation normally unmounts the component, and navigation clicks dismiss it before switching context. Panels are viewport-constrained, scrollable and positioned above the trigger when there is insufficient room below; opening them must not change table row height.

Use a separate help trigger for disabled controls that need an explanation. Native `title` may supplement an action's visible/accessibility label, but must not be the only way to read substantive help. Do not add a second bespoke tooltip implementation. Keep native popovers as read-only help, not a replacement for the dialog host or an authorization boundary.

Before shipping a migrated use, check tap and keyboard activation, Escape/focus return, outside interaction, one-open behavior, page and nested scrolling, scrolling long panel content, viewport edges at narrow widths, light/dark themes and unchanged surrounding layout. Pure positioning regression cases live in `tests/unit/popover-position.test.ts`; dismissal and native activation require a browser check.

## CSS

Headings and column headers use title capitalization via `index.css`; existing explicit uppercase styles remain uppercase. This is presentation only and does not rewrite stored character, raid or item names. Help-popover body text keeps its original sentence case.

`App.css` holds the shared layout and primitive styles and is global. `./App.css` must stay the last stylesheet import in `App.tsx`: several selectors rely on load order and on `:nth-child` positions, so do not add wrapper elements or reorder children inside existing components. A feature that needs new styles adds its own stylesheet with a unique prefix on every class (for example `.cov-...`), imports it from the feature, and does not edit another feature's stylesheet. `AfkCalendar.css` is the existing example.

Keep `.table-scroll` positioned: it contains absolutely positioned accessibility labels inside wide tables. Without that containing block, visually hidden column labels can escape the table's scroll boundary and widen the mobile page. Verify the document stays viewport-width while the table and mobile navigation still scroll independently; root-level overflow clipping alone does not prevent this.

## Known quirks (unchanged on purpose)

The notice banner is never cleared, and the error and notice banners persist across tab switches. The history footer shows the filtered count for both numbers. Assigning, unassigning and reordering do not set the busy flag. The "last Guild Leader" guard is UI-only. The modal has no Escape key or focus trap. These predate the module split; fix them in their own PRs.
