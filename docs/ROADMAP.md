# Roadmap, decisions and work lanes

Last updated 2026-11-11. This file records direction, policy decisions, milestones and work lanes. [backlog.json](backlog.json) is the canonical item/status tracker; [the changelog](../CHANGELOG.md) records verified releases. Feature-status descriptions below provide context, not a second independent tracker. Keep them consistent with those files and follow [the maintenance rules](../CONTRIBUTING.md#backlog-patch-notes-and-publishing).

## Dates that drive the order

- **2026-11-04** WoW: Forever launch, not a full-app delivery deadline. The launch adoption targets for roster comment review (`MEMBER-004`) and the first mobile usability pass (`UX-002`) were delivered; continue collecting and reproducing mobile reports. Roll out other core web-app functionality progressively between launch and December 9; roster, access, teams and calendar usability come first.
- **2026-12-09** the first raids unlock (Barrow Deeps 10, Hyjal Summit 20, Onyxia 40). Scheduled raids and sign-ups must be ready for members to use in advance of that night's raid, with the first immutable starting roster/sign-up snapshot taken at its scheduled start on December 9. These are firm requirements, not part of the optional delay.
- **First-raid loot, 2026-12-09:** target recording awards from the first raid without requiring priority listings. Use need-before-greed rolls until priorities are adopted. If app recording is not ready, leaders record loot in a spreadsheet and a later upload workflow preserves those awards; that upload is planned, not available today.
- **Around 2026-12-15:** begin using priority listings. Recording a receipt and deciding its recipient by priority are separate capabilities; recording must not require an active priority list.
- **2026-12-22:** target full rollout of all planned functionality, including loot audits, priorities, the production addon, Discord and advanced automation. These are targets, not claims of implementation. If everything is ready, the full rollout may start December 9; otherwise soft-open over the first one or two weeks of raiding. December 9 scheduling, sign-ups and the first snapshot do not slip with this broader rollout.
- **About 2026-10-21 and 22** the beta ends. Game data in the app (buffs, debuffs, scopes) must be re-checked then, in launch week, and on 12-09.

Core web-app functionality is what "most functionality" means for the November 4 to December 9 window; it excludes the addon, Discord and advanced automation. Those remain in the broader December 22 target. Targets do not override validation, authorization or immutable-history requirements; record and explicitly agree any change of scope or date rather than silently treating unfinished work as complete.

## Scheduled-raid lifecycle agreed 2026-10-19

This is intended behavior, not a release announcement. It supersedes earlier assumptions that invitations come only from assigned teams/reserves or that standing assignments remain the editable roster for a scheduled raid. The earlier dynamic-team expansion, alternate naming themes and Primary/Secondary team-set discussion was scrapped; none of that is approved scope.

### Eligibility and terminology

- **Invitations are per member:** invite anyone whose main character is marked ready to raid, whether assigned to a standing team or not. A ready alt alone does not qualify a member with an unready main for an invitation.
- **Raid Teams available roster is per character:** include every raid-ready character, mains and alts. A ready main does not qualify an unready alt. Deployed with RAID-011; retain the existing All characters / Hide alts presentation choice within the eligible list.
- Team members and ready reserves are collectively **raiders**. Being outside a standing team must not imply a permanent bench identity. A **bench position** belongs to a particular scheduled raid.
- Readiness does not grant guild access or guarantee a raid position. Invitation eligibility is not, by itself, a newly approved restriction on who can submit a sign-up.
- The deployed Leadership Overview uses the scheduled invitation list for missing responses; retained invitations still count after readiness loss. The historical MEMBER-003 scope below is not the new invitation rule. Coverage uses independent standing assignments, not scheduled positions.

### Lifecycle and sequencing

1. Maintain characters and independent readiness in the roster. Maintain independent standing assignments for 10/20/40; one character may have a separate assignment at each size. Existing 10-player assignments stay; 20/40 begin empty.
2. At creation, establish main-ready invitees and copy standing positions once, immediately, including unready assigned characters with warnings. Independent lineups exist for each size, shared by zones of the same size that night; there is no 10-to-20-to-40 derivation. Subsequent standing edits never update this raid. Unassigned invitees remain available/unassigned, not automatically benched.
3. Collect the member's response separately from their active or bench placement. Preserve one response per account, owned-character selection, unavailable-date enforcement, cancellation and start cutoff.
4. Up to start, Guild/Raid Leaders edit only this raid's active/bench positions. New placements use the member's selected ready character, or ready main before a response, labelled Not responded. Capacity is a hard limit and the same player cannot have two characters in one individual team; different teams of the same size may contain different characters of that player. All response states may be placed, but Absent/unavailable requires explicit acknowledgment. Pre-start positions need no visible audit history; preserve the original snapshot and audited in-raid correction requirement separately.
5. Later Discord automation announces the raid and requests confirmation, reminds unconfirmed invitees 24 hours and 1 hour before start, and requests bench readiness 30 minutes before start. Bench credit requires the readiness confirmation; do not infer it from an Accept or voluntary Bench response.
6. At the scheduled start, freeze that raid's working lineup, bench assignments and sign-up state for reference and the attendance baseline. Subsequent standing-team edits cannot change it; later in-raid changes/corrections are separate and audited. Neither the snapshot nor a sign-up proves actual attendance.
7. Record actual participation and qualifying bench readiness before computing rolling attendance reports.

RAID-001 later delivered immutable snapshots of the working roster, and RAID-014's five-minute sweep was deployed in `6721a31`. Dynamic team expansion, automatic allocation, Discord automation, attendance calculations and loot changes were not part of RAID-011. The December 9 first-raid requirement remains unchanged.

### Discord sign-ups and notifications
- **Discord sign-ups and notifications (December 22 target).** Not started; needs raid edit and cancel (item 6, done) first. The bot is planned, but the exact reminder delivery behavior still needs agreement. In order:
  1. A Discord user ID on members, set by a Guild Leader in Member Access, so a sign-up maps to a roster character and its main.
  2. Announcements through a channel webhook (a Cloud Function) when a raid is scheduled, changed or cancelled. One-way.
  3. Sign-up buttons on a bot-posted message, mapped to the app's existing response states and character choices. Discord calls an HTTPS interactions endpoint (a Cloud Function) that verifies Discord's request signature and the member's identity, character ownership, cancellation, unavailable dates and start-time cutoff, writes the same `raids/<raidId>/signups/<uid>` document, and updates the message. Direct client writes are denied; Discord must reuse the server-side authorization and availability transaction serialization, not bypass the existing callable guarantees.
  4. Invite members with a ready main at creation; remind unconfirmed invitees 24 hours and 1 hour before start. Request readiness from the scheduled raid's assigned bench 30 minutes before start, required for bench attendance credit. Use scheduled server work and the scheduled-raid data contract; attendance rolls up to the main. Exact confirmation-state targeting and response windows remain open.

Configure Cloud Scheduler as needed; keep the bot token and webhook URL in function secrets, never in the repo or client; configure the Discord public key server-side. ## How to avoid stepping on each other

- Changes to the shared files listed in `AGENTS.md` get their own commit and a note in the pull request.
- If you touch `firestore.rules`, add or update the matching test in `tests/rules/` and run `npm run test:rules`.
- One format-everything commit is deferred: it conflicts with every open branch, so it only makes sense when no branch is open.
- Say in the pull request which lane an item belongs to, so two people do not start the same thing.
